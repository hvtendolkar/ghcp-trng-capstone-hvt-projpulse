# AI Agent Instructions for PRD & Product Documentation

## Purpose
Ensure all Product Requirements Documents (PRDs) and major product documentation maintain consistency, comprehensiveness, and professional quality.

## Scope
Applies to: `*.prd`, `PRD*.md`, `*_PRD.md`, `product_requirements*.md`, and similar product documentation files.

---

## Structure & Organization

### Required Sections (in this order)
1. **Header with Metadata**
   - Title
   - Version number
   - Date created
   - Status (Draft, In Review, Approved)

2. **Executive Summary** (Section 1)
   - Product name and tagline
   - Brief overview (2-3 sentences)
   - Key objectives (3-5 bullets)

3. **Vision & Objectives** (Section 2)
   - Product vision statement
   - Primary objectives aligned with business goals

4. **Target Users & Personas** (Section 3)
   - 2-4 primary user personas with demographics
   - User scenarios and use cases

5. **Features & Capabilities** (Section 4)
   - Organize by phase (MVP, Phase 2, Phase 3, etc.)
   - Subsections for each feature category
   - Clear descriptions of functionality

6. **Technical Requirements** (Section 5+)
   - Architecture overview
   - Technology stack with rationale
   - Security & compliance requirements
   - Performance & scalability requirements
   - Infrastructure specifications

7. **Integration Details** (if applicable)
   - Third-party API/service integration specifics
   - Workflow diagrams or descriptions
   - Fallback mechanisms and error handling

8. **Non-Functional Requirements**
   - Performance metrics (response time, throughput, uptime)
   - Scalability and reliability targets
   - Usability and accessibility standards

9. **User Experience & Design Flows**
   - Key user journeys
   - Interaction patterns
   - Error handling from UX perspective

10. **Success Metrics & KPIs** (Section 9+)
    - Business metrics (cost, adoption, revenue)
    - Operational metrics (deflection rate, resolution time)
    - Quality metrics (accuracy, uptime)
    - User engagement metrics (DAU, retention)

11. **Product Roadmap** (Section 10+)
    - Phased rollout with timelines
    - Key milestones per phase
    - Launch dates and dependencies

12. **Risks & Mitigation** (Section 11+)
    - Table format: Risk | Impact | Probability | Mitigation
    - 8-12 key risks identified

13. **Dependencies & Constraints** (Section 12+)
    - External dependencies
    - Internal dependencies
    - Budget, timeline, regulatory constraints

14. **Success Criteria** (Section 13+)
    - Launch readiness checklist
    - Business success criteria (6-12 month targets)

15. **Glossary** (Section 14+)
    - Define domain-specific terms
    - Acronyms and their meanings

16. **Appendix** (Section 15+)
    - Additional technical details
    - Technology stack summary table
    - Resource allocation breakdown
    - Timeline and milestones summary
    - Approval sign-off section

## Content Guidelines

### Executive Summary
- Keep to 2-3 paragraphs maximum
- Include vision, objectives, and market positioning
- Make it accessible to C-level executives

### Features Section
- Group logically by category or user type
- Use Phase structure: MVP → Phase 2 → Phase 3+ for feature rollout
- Each feature should have clear description and business value
- Use bullet points for clarity

### Technical Requirements
- Provide specific technology choices with rationale
- Include performance benchmarks and SLAs
- Detail security protocols and compliance standards
- Specify scalability requirements and architecture patterns

### Metrics & KPIs
- Use 4 metric categories: Business, Operational, Quality, Engagement
- Provide specific targets (e.g., "≥ 95%", "< 2 seconds")
- Include measurement methodology where relevant

### Roadmap
- Clearly label phases with duration (e.g., "Months 1-3")
- Show dependencies and critical milestones
- Include launch dates and expected outcomes

### Risks Section
- Use table format for consistency
- Include: Risk statement | Impact (High/Medium/Low) | Probability (High/Medium/Low) | Mitigation strategy
- Order by impact × probability

## Formatting Standards

### Markdown
- Use proper heading hierarchy (`#` to `#####`)
- Separate sections with clear visual breaks
- Use bullet points for lists; numbered lists for sequences

### Tables
- Use for: metric comparisons, timeline summaries, risks, resource allocation, technology stack
- Include headers; keep content concise
- Align content for readability

### Code/Technical Content
- Use backticks for inline code
- Use fenced code blocks for configuration or examples
- Syntax highlight when possible (e.g., ` ```json ` for JSON)

### Emphasis
- **Bold** for key terms and important values
- *Italics* for definitions or asides
- Avoid ALL CAPS; use bold instead

---

## Tone & Voice

- **Professional & Formal:** Appropriate for stakeholder communication
- **Clear & Concise:** Avoid jargon where possible; define technical terms
- **Action-Oriented:** Use active voice; focus on deliverables
- **Objective:** Data-driven; avoid superlatives unless backed by metrics
- **Comprehensive:** Include sufficient detail for implementation teams

## Metadata & Sign-Off

### Header Metadata
```
# Product Requirements Document (PRD)
## [Product Name]

---

**Product Name:** [Clear, memorable name]
**Version:** [e.g., 1.0]
**Date:** [Creation date]
**Status:** [Draft | In Review | Approved]
```

### Footer Information
Include at document end:
- Document Owner
- Last Updated Date
- Next Review Date
- Version Number
- Current Status

### Approval Sign-Off Section
Include table with:
- Role (VP Product, CTO, Chief Compliance Officer, CFO, etc.)
- Name (if approved)
- Signature line
- Date

## Examples of Strong Patterns (from Banking Chatbot PRD)

✅ **Executive Summary:** Includes product name, version, date, overview, and key objectives in concise format

✅ **Feature Organization:** MVP phase clearly marked with subsections for feature categories (Conversational Capabilities, Account Management, Card Services, etc.)

✅ **Technical Section:** Specific model config (Gemini 2.0 Pro), context windows, temperature settings, token limits

✅ **Success Metrics:** Four distinct categories (Business, Operational, Quality, Engagement) with specific, measurable targets

✅ **Risk Table:** Clear columns for Risk | Impact | Probability | Mitigation Strategy, ordered by severity

✅ **Resource Allocation:** Table showing Role | Count | Notes for staffing clarity

✅ **Roadmap:** Phased breakdown with month ranges, key deliverables, and launch dates

## When in Doubt

- **Too much detail?** Move to appendix or create separate technical specification document
- **Missing section?** Check against the Required Sections list; if applicable, add it
- **Unclear metrics?** Make them SMART (Specific, Measurable, Achievable, Relevant, Time-bound)
- **Formatting questions?** Follow the style of the Banking Chatbot PRD template
- **Tone concern?** Read aloud; should sound professional but not robotic

---

## Common Mistakes to Avoid

❌ Vague success criteria ("users will be happy")  
✅ Specific metrics ("CSAT ≥ 4.5/5.0")

❌ Incomplete roadmap ("Build features in Q1")  
✅ Detailed roadmap ("Months 1-3: MVP development and testing; Month 4: Phase 1 Launch")

❌ Missing technical specifics ("Use cloud infrastructure")  
✅ Specific details ("Google Cloud Platform (GCP), multi-region deployment, Kubernetes on GKE")

❌ Unquantified risks ("Security might be an issue")  
✅ Quantified risks with mitigation ("Security breach/data leak | Critical Impact | Low Probability | Regular security audits + penetration testing + SOC 2 compliance")

❌ Approval section with no names ("To be signed by stakeholders")  
✅ Clear approval section ready for sign-off with designated roles

## Document Template Quick-Start

When creating a new PRD, use this minimal structure as starting point:

```markdown
# Product Requirements Document (PRD)
## [Product Name]

**Version:** 1.0 | **Date:** [Date] | **Status:** Draft

## 1. Executive Summary
[Overview, vision, objectives]

## 2. Product Vision & Objectives
[Vision statement and primary goals]

## 3. Target Users & Personas
[User profiles and scenarios]

## 4. Key Features
### Phase 1 (MVP)
[Features for MVP]

### Phase 2
[Future features]

## 5. Technical Requirements
[Architecture, tech stack, performance, security]

## 6. Success Metrics & KPIs
[Measurable targets for business, operations, quality, engagement]

## 7. Product Roadmap
[Phased timeline with milestones]

## 8. Risks & Mitigation
[Risk table with mitigation strategies]

## 9. Dependencies & Constraints
[External/internal dependencies, constraints]

## 10. Success Criteria
[Launch readiness, business success criteria]

## 11. Appendix
[Additional details, technology stack, resource plan]

---
**Document Owner:** [Name]  
**Last Updated:** [Date]  
**Status:** Draft
```
